# Plan: rule documentation and the site

The rule pages of the public site: what they say and how they read. Build and data flow today: [site.md](../development/site.md). Style references: the rule pages of Ruff and Biome, ESLint's rule list, Clippy's lint list (look for structure, never copy text or styling).

## Part A: site (one step)
All work is in `site/`, `xtask/full/src/rules.rs` and the parity catalogs; no product code.

1. **Configuration examples.** A rule without options is shown in the short form `rule-id: warn  # off (default), warn, error`; a rule with options keeps `level` and `options`. The schema and the config loader already accept both.
2. **Upstream table of a rule page.** "Measured for the tool" goes: it is one number for the whole tool (the share of the findings of its default set that Sudsy also reports) and says nothing about this rule; it stays on the tool's own page. "Coverage" becomes "Match": `full` (reports what the upstream rule reports) or `partial`, with the catalog's note saying what differs; a sentence above the table explains it.
3. **Links to the upstream rule.** Each tool's catalog gets a `rule-url` template (`{id}`, and `{id-lower}` or a per-entry override where the URL needs something else), and the rule's id in the table links there; the tool name keeps linking to our comparison page. `rules.json` carries the resolved URL (`url`), so `sudsy rules` and the agent docs get it too; a rule with no page of its own (a setting, a rule list with anchors) uses the anchor of the list; a tool without any per-rule page says so in its catalog (`rule-url: none`), so a missing template fails codegen. A script checks that every URL answers (status 200 after redirects, the anchor present), run by hand and in the nightly, never in the gate. The comparison pages link their ids the same way.
4. **Rule page layout.** A header block in place of the sentence "Languages: ... Category: ... Fix: ...": badges for language (linked), category, fix kind, default level and presets. Then "What it does", "Why it matters" (part B), the example as bad and good blocks, configuration with the options table, upstream table. The example of a page is at most about 25 lines: a longer fixture input is cut to the lines around the reported spans (context 3, `...` between), squiggles and the fixed text recomputed or left out when the cut makes them wrong.
5. **Rule list.** A real table: rule, languages, category, fix, upstream ids, one line of description, with fixed column widths that wrap badges, not one line of tags behind the name. All rules are listed, none cut off; no paging. Rows are rendered into the page from `rules.json` and filtered in the browser (no request per rule, so the list works in `dev` too); the search box matches id, description and upstream id; query parameters (`?language=`, `?preset=`, `?q=`, ...) keep working. Pagefind stays for the header search only; the filter chips it needed on rule pages go when nothing reads them.
6. **Filters.** Compact controls in one row above the list: one menu per filter (language, category, fix, preset, upstream tool) with a search field inside for the long ones, counts per value, the selected values as removable chips, a "clear" button; on a narrow screen they collapse into one panel. Keyboard and screen reader usable (labels, `aria-expanded`, focus visible), light and dark theme, no horizontal scrolling at 360 px.
7. **Text.** The site's tagline and description are "Fully featured polyglot formatter and linter for 20+ languages. Extremely configurable, plugin-extendable." (landing page front matter, hero, and other generic descriptions of the product on the site). Language pages, tool pages and the preset and format-option pages get the same table and badge styles; long tables keep their header in view.
8. **Check.** Extend `site/test/smoke.mjs` (all rules listed, each filter, short config form, upstream links, badges); screenshots of the rule list, two rule pages, a language page and a tool page, light and dark, desktop and 360 px, before and after, handed to the lead. Page weight of the list and the time of the first filter are recorded in `docs/ai/performance/numbers.md`; `scripts/site.sh scale-test` must stay usable at 10,000 rules.

## Part B: rule descriptions (steps per language)
State: 833 rules; the median description is 104 characters, 345 are under 90. A rule needs two texts.

- `description` ("What it does"): what the rule reports, in plain words, complete enough to decide whether a case is reported, with the exceptions and the options that change it. Upstream rule names do not belong in it: the table has them.
- `why` ("Why it matters"): the concrete harm (a bug, a security or performance problem, a reader's confusion), one to four sentences, and for a style rule the reason for the convention without inventing a danger. A text that fits any rule ("improves readability") is rejected.
- For a rule whose fix is not obvious, how to repair the code; the fixed example shows it.

Mechanism (first step, one pilot language): `RuleMeta.why` and the YAML key `why`, in `rules.json`, the site, `sudsy rules <id>` and the Markdown twins; the JSON schema and the editor's message keep the first sentence of `description`. The first sentence of `description` stands alone. A list of rules without `why` is checked by codegen and may only shrink; a new rule needs both texts (`cargo xtask new-rule` writes the keys). Measure the binary size of the texts first: above 0.3 MB in total, the long texts go into `rules.json` and the site only, with the CLI reading none of it.

Writing: facts come from the rule's code, its options and fixtures, then the upstream's documentation is read for what it warns about; text is our own (no copying: licences and accuracy). Where the text and the code disagree, the code is checked: a wrong rule is a bug entry with a test, not a vaguer text. Batches of 80 to 120 rules by language, the pilot (Dockerfile, 50 rules) first: the lead and the user read it before the rest starts. Each batch is read by a second agent against the code for a sample of 15 rules; more than one false statement in the sample sends the batch back.

Order after the pilot: Python, JS and TypeScript, C#, shared rules, then the languages by rule count.

# Design: the symbol index

Status: plan. The user decided on 2026-11-24 to build it. Phases below; the lead reviews at each checkpoint.

## What it answers
Which types, functions, constants and members exist, in which file, with which parents and parameter counts. It answers by name: "is there a class `App\Foo`", "does `Foo` or an ancestor have a method `bar`, static or not, with how many parameters".

It does not infer the type of an expression. A rule may use a receiver whose class is written in the source (`$this`, `self`, `static`, `parent`, `Name::`, `new Name`), nothing else. Types of variables stay with each language's reference checker through a worker (roadmap); that decision is unchanged.

## What exists already
- `Rule::collect` / `finish` (`core-rules/project.rs`): string facts per file, joined once all files are seen, at `analysis: deep` or per directory. The facts belong to one rule and cover the linted files only; nothing reads dependencies. `core-incremental/module.rs` shows the salsa shape to follow: facts are a query of one file, the join is a query over the files.
- `core-semantics::scopes`: names inside one file. It stays the model inside a file; the index holds what a file declares to others.
- C#: Roslyn answers this in the worker. It does not move onto the index.

## Parts
| Part | Where | What |
|---|---|---|
| Declarations of a file | `core-semantics::symbols` | `FileSymbols`: the types (qualified name, kind, abstract / final, parents, used mixins, members), functions and constants a file declares, and whether a declaration is conditional. Built from the Sudsy tree by kind sets and roles that the language passes, never from a parser's own AST, so a replaced parser changes nothing here. A salsa query of `parse`: an edit inside a body yields equal symbols and invalidates nothing else. |
| Name resolution in a file | `core-semantics::symbols` | namespace, imports and aliases, relative names. One resolver with the language's options (separator, case folding per kind, fallback to the global namespace). |
| Finding the file of a name | `Locator` trait, one implementation per package system in a shared crate | The project's own files, then dependencies. Composer: PSR-4 and PSR-0 prefixes, class map, autoloaded files of `vendor/composer/installed.json` and `composer.json`. Data in, path out. |
| Dependencies on demand | `core-incremental` | A dependency file is read and parsed only when a name in a linted file resolves into it, through salsa inputs of their own (no rule runs on them, no diagnostics). Function files that a package autoloads are read once. The 142 MB of vendor code of the PHP corpus are not parsed as a whole. |
| Built-ins | generated data in the language pack | PHP's own classes, members, functions with parameter counts and version range, generated by a script from a pinned source; its license is checked first. Compact binary or string table, loaded lazily. |
| Answers | `Index` | `Known(&Symbol)`, `Absent`, `Unknown`. `Unknown` wherever a fact is missing: no manifest found, a file that does not parse, an unresolved parent, a dynamic member (`__call`, `__get`), a conditional or computed declaration. A rule reports only on `Absent`. |
| Rules | `core-rules` family `index_rules` | unknown type, unknown function, unknown member on a named receiver, argument count. Off by default; a rule declares that it reads the index, so a run without such a rule does nothing. |

## Rules of the design
- **No false report from missing knowledge.** `Absent` needs proof: the locator is complete for that name (the manifest covers its prefix, or every project file was read). A project without installed dependencies gets `Unknown` for everything outside itself, not thousands of reports.
- **Off costs nothing.** No index rule active: no query runs, no file is read. The bench shows 0 on every metric of a run without index rules, startup included.
- **The editor works.** An edit recomputes `FileSymbols` of one file; dependents re-run only when its symbols changed. Budget: 20 ms after an edit in a 6,000-file project, memory reported.
- **Language facts only in the language crates.** Kind sets, name rules and the built-in data. A data row format appears only when a second language reads it (two-language rule); until then the languages pass plain kind sets.

## Languages
| Language | Use | Evidence |
|---|---|---|
| PHP | unknown class, function, member, argument count | PHPStan level 0 |
| Protobuf | cross-file rules of buf: `RPC_REQUEST_RESPONSE_UNIQUE` 117 missed, `IMPORT_USED` 5 | buf coverage |
| JavaScript / TypeScript, Python, Java, Kotlin, Ruby | unresolved imports, unused exports, names a module does not export | not measured; after the first two |

Protobuf is the second user and proves that the parts are not shaped like PHP. Its locator is the import path list.

## Phases
1. **Measure (checkpoint).** PHPUnit in the corpus, PHPStan re-measured. Every remaining finding is classified by the smallest knowledge it needs: own file; a name in the project; a name in dependencies; a built-in; a member of a written class; a type of an expression; a PHPStan-only fact. The result says what share the index can reach. If it is under 85%, the lead brings the number and the other options to the user before phase 2.
2. **Symbols and resolution**: `FileSymbols`, the resolver, the salsa query, project files only; PHP and Protobuf both extract. Tests per construct; extraction time and memory over the PHP corpus.
3. **Locator and dependencies on demand (checkpoint)**: Composer and Protobuf imports; `Unknown` / `Absent` tests; editor latency and memory.
4. **Built-ins**: generator, license, size in the pack.
5. **Rules**: in order of findings, each with covered and extra counts. Extra reports on the corpus are explained one by one; a rule with more extra than covered stays out of the preset.
6. **Protobuf rules**, then the generalization review: what did the second language change, which facts become rows.

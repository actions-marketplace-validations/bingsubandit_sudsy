# Design: the Java parser

Goal: decide what to do about `rezel-lang-java` (`=0.0.0`, behind `lang-java`'s adapter): two known bugs ([../bugs.md](../bugs.md)) and a one-author upstream. The standard is the parser comparison of [../architecture/adding-a-language.md](../architecture/adding-a-language.md#parser-comparison-before-step-1) and decision 4 of [shared-core.md](shared-core.md). The user decides; nothing is built. The measure crate is `.cargo/tmp/p3/m` of the measuring worktree (one cargo feature per parser, a counting allocator, one `probe` mode).

## 1. Comparison (measured, not committed)
Linux arm64 Neoverse-V2 (Graviton), 8 cores, rustc 1.99.0, release with fat LTO and one codegen unit for speed, parse of whole files from memory, one thread, warm, best of 5, no adapter. Corpus: the 5,337 files (48.8 MB) of `tests/conformance/fetch-java-corpus.sh` (Guava, Gson, Error Prone, Commons Lang, google-java-format with its test inputs; pinned commits there). Probes: 18 one-feature files (records with compact constructors, sealed/non-sealed, `switch` patterns with `when`/`yield`, record patterns, `var`, text blocks with and without `\"""`, lambdas and method references, enums with bodies, annotation types, bounded generics and intersection types, unnamed `_`, `module-info`, labels, literals, inner-class creation, `>>>` against generics, comments) and nesting inputs (chains of 100-1,000 calls; 500-10,000 nested parentheses and blocks). Mutants: one `)`, `}` or `]` deleted from 500 valid files of 0.5-40 KB.

## 2. Findings
- rezel has the lowest memory, the second best speed, and two failures in 5,337 files. The first is real only in builds with debug assertions: in release the text block is a recovery node, so the file is refused like any parse error (the formatter leaves it as written). The second is a limit: a call chain longer than about 350 links, or one call per line from about 300, produces recovery nodes. Neither bug is in the adapter.
- rezel is a pre-release (`0.0.0`) from one author, seven weeks old, with the grammar ported from Lezer (CodeMirror's). It is pinned exactly, so nothing moves under us; the risk is that a fix never comes. The code involved is `rezel-lr` (7.7 k lines): vendoring it as a patched crate is the same shape as `third_party/mago-*`.
- tree-sitter-java has no deficit that rezel does not have except one construct (a type-use annotation on varargs, 0.26 % of the corpus, Guava style) and it is 42 % slower; but the published grammar is 23 months old, so the fix is a fork of `grammar.js` under [../development/grammar-forks.md](../development/grammar-forks.md), and the move costs the Java kind table (149 node kinds named after rezel's, with 45 role tags) and the 1,694 lines of formatter and the rules that match on those kinds. Its trees tile; rezel's need the 40-line `fill` in the adapter.
- cure-java-parser is the fastest and smallest, but its tree has no spans and it aborts the process on deep nesting: not a candidate for a lossless tree.
- Hand-written (estimate, not built): a lossless Java 21 recursive-descent parser on our tree is about 3,500-4,500 lines (lexer 700, declarations and types 1,500, statements 600, expressions with precedence 900, recovery and the adapter-free tree building the rest), against cure's 5.3 k lines with no spans. That is over the 1,000-line guide of decision 4, and the language is large and moving (a release every six months); the upside would be our own recovery and no pre-release dependency.

## 3. Recommendation
**Keep rezel** (`=0.0.0`) and handle the two bugs where they are:
1. Report both to upstream with the two corpus files (`FormatterTest.java`, `WellKnownMutability.java`) and a chain of 400 `.add("x")` calls as the minimal chain input (a one-line text block with an escaped `\"""` parses; the reducing input of `FormatterTest.java` is still to be found).
2. If upstream has not fixed them when Java's role and layout steps (R2, L1) start, vendor `rezel-lr` (and `rezel-lang-java` if the grammar needs it) in `third_party/` with the fix, as for mago. Until then `conformance` keeps naming both files.
3. Fallback, if rezel is abandoned or the patch is too large: tree-sitter-java as a fork with the varargs-annotation fix behind `core-treesitter`, at the cost named above; it needs no hand-written parser. A hand-written parser is for the case where both fail; do not start it now.

Costs accepted: a one-author pre-release dependency with a path to a vendored fork, two refused files in 5,337, the adapter's gap filling for the tokens Lezer leaves out, and a 350-link limit on call chains (real code with more is rare; Error Prone's `WellKnownMutability` is the one in the corpus).

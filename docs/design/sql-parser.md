# Design: the SQL parser

Goal: decide whether `lang-sql` stays on sqruff (`sqruff-lib-core` / `-dialects` `=0.44.0`; ansi, postgres, mysql, tsql) or moves, by the standard of [../architecture/adding-a-language.md](../architecture/adding-a-language.md#parser-comparison-before-step-1) and decision 4 of [shared-core.md](shared-core.md). The user decides; nothing is built. The measure crate is `.cargo/tmp/p3/m` of the measuring worktree (one cargo feature per parser, a counting allocator, one `probe` mode).

## 1. Comparison (measured, not committed)
Linux arm64 Neoverse-V2 (Graviton), 8 cores, rustc 1.99.0, release with fat LTO and one codegen unit for speed, parse of whole files from memory, one thread, warm, best of 5, no adapter. Corpus: sqlfluff `0511a32` dialect fixtures (ansi 214 files / 37 KB, postgres 210 / 183 KB, mysql 258 / 66 KB, tsql 195 / 194 KB; the files sqlfluff's own parser accepts, so a failure is a gap of the parser) and the PostgreSQL regression inputs, postgres `81b2179` (245 files / 5.1 MB; 113 hold psql `\` commands and many hold statements that must fail, so the 132 files without a `\` line, 1.9 MB, are the fairer set). Probes: 22 one-feature statements (pg 10: `DISTINCT ON`, `ON CONFLICT`, `->>`/`#>`/`::`, dollar-quoted body, `FILTER`/window frames, `LATERAL` with `GROUPING SETS`, `MERGE`, identity columns, `CONCURRENTLY`/`gin`, `FOR UPDATE SKIP LOCKED`; mysql 5; tsql 5: `TOP`/`NOLOCK`, `DECLARE @`, `CROSS APPLY`, `TRY/CATCH`, procedure; ansi 2). Mutants: one `)`, `}` or `]` deleted from files of 0.5-40 KB the parser accepts (n is small because few files qualify). "Failure" is what the parser reports: an `Unparsable` segment or lex error (sqruff), `Err` (sqlparser), an `ERROR` or `MISSING` node (tree-sitter). The tree-sitter grammars have no dialects: one run per file set.

## 2. Findings
- sqruff is the only candidate that builds a tree whose leaves tile the file and that has tsql, mysql and postgres grammars with no probe failing. Its cost is speed (0.4-0.6 MB/s, 25 times slower than sqlparser-rs on the files that parse) and memory (about 650 bytes per input byte, hence the 512 KB file limit of `lang-sql`). Its failures on the fixtures are mostly DDL and procedural syntax (postgres 30 %).
- sqlparser-rs is the fast one (10-13 MB/s, 50-180 B/B) and has the widest dialect list, but it fails more fixtures than sqruff in every dialect (mysql 61 %, tsql 75 %), has no error recovery, and its AST is not a concrete tree: it would be a token list plus a tree we derive ourselves, which is the hand-written parser's work without its grammar. Out as a replacement.
- tree-sitter-sequel is generic and fails 37-92 % of the fixtures: out. tree-sitter-postgres is the strongest on Postgres (12 % of the fixtures, 24 of 132 regression files, which include statements that must fail; best recovery; 6-8 MB/s) but is Postgres only, 15 MB of binary, one maintainer and a beta: it cannot be the SQL parser; it could be a second provider only if Postgres were worth its own language.
- Real dialect coverage is the bottleneck in all of them; none is a clear win over sqruff on failures except tree-sitter-postgres on its one dialect.
- Hand-written (estimate, not built): decision 4 of the shared-core design allows it because four dialects can share one parser. A parser that is lossless, recovers per statement and covers queries, DML, the common DDL and procedural blocks is about 5,000-7,000 lines (lexer 700; statements and clauses 2,500; expressions 800; dialect tables as data 1,000; the rest dialect hooks), against 34 k lines of sqruff's four dialects and 75 k of sqlparser-rs. Every statement kind it does not know becomes an opaque statement up to the next `;` (the formatter keeps it as written), so its failure rate is by construction a share of opaque statements, not parse errors; it would run at 20-50 MB/s with a few bytes of memory per input byte. The cost is the grammar of each dialect written once more by us, a growing list for DDL, and the 3,000-line budget of decision 3 (a review is needed).

## 3. Recommendation
**Keep sqruff for now** (`=0.44.0`), with its present guards (512 KB limit, panic catch). It has the best failure counts of the Rust parsers, tiles the source, and a company behind it; replacing it with sqlparser-rs or a tree-sitter grammar loses coverage in every dialect. Costs accepted: 0.4-0.6 MB/s and 650 B/B (a 512 KB file takes 1-2 s and 330 MB), 30 % of the postgres fixtures reported as parse errors (those files stay as written), one panic path under `catch_unwind`, a pre-1.0 pin that moves by hand.

**Plan to replace it by a hand-written statement-level parser** when SQL formatter parity or speed becomes the limit, not before: it is the one option that removes the speed, memory and opaque-DDL problems together, with the four dialects as tables. Trigger: the formatter's failure share on real code (sqlfluff parity: 674 of 867 accepted files identical today) is limited by sqruff parse errors rather than layout, or a repository run needs more than the 512 KB limit. First step of that plan: the sketch above measured on the same fixtures (opaque-statement share per dialect) before any build.

Do not adopt sqlparser-rs, tree-sitter-sequel or tree-sitter-postgres.
